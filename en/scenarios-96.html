Scenarios

Scenarios (workflows) automate processing in your application: sending an email, updating data, calling an external service, etc.

Each scenario is made of a trigger that defines when it starts, and a sequence of steps (actions) that define what it does.

The Scenarios space

Scenarios are managed from the Scenarios tab of the design tool.

The left panel lists the application's scenarios. A search field and filters (All, Click, Planned, Webhook, Table) help you find a scenario quickly. The trigger is displayed under each scenario name, for example Planned - Daily (12:00).

The right panel displays the steps of the selected scenario. The Actions button adds steps, which are then linked together starting from the Start block.

When hovering a scenario, buttons let you, depending on its type, rename or edit it, run it manually, view its execution history, display its usages or delete it.

Available actions are detailed in the Actions page.

Create a scenario

Click Create scenario at the bottom of the list, then enter a name and choose a trigger.

Trigger Description
User clickStarts when someone taps or clicks inside the app
Planned runRuns automatically at a chosen time or rhythm
WebhookLaunches when an external service sends a request
Table eventStarts when a row is created, updated or deleted in a table

Depending on the selected trigger, a configuration window opens to enter the scenario name and its settings.

User click

A Click scenario is a shared scenario: it can be reused from several screens or from other scenarios, instead of duplicating the same actions.

The Usages button lists the screens and scenarios that use it.

A shared scenario that is still in use cannot be deleted. Remove its usages first.

Planned run

A scheduled scenario runs automatically according to a frequency.

Frequency Settings Example
Hourly-Will run every hour.
DailyHour (0-23)Will run every day at 12:00.
WeeklyDay of the week, HourWill run every Monday at 8:00.
MonthlyDay of the month (1-31), HourWill run every month on day 1 at 6:00.

Scheduled scenarios run at the top of the hour. The Run manually button lets you test a scheduled scenario without waiting for its next trigger.

With a monthly frequency, a day that does not exist in the month (for example the 31st) is not executed that month.

Table event

A Table scenario starts automatically when data changes in one of the application's tables.

Choose the Table to watch, then the Event:

  • Any change
  • Row created
  • Row updated
  • Row deleted

Webhook

A Webhook scenario is triggered by an external system (ERP, CRM, script, another application...) sending an HTTP POST request to Zyllio.

Webhook URL

The URL is generated automatically and displayed in the webhook configuration window. It looks like this:

https://<your-application-host>/api/workflow/<application-id>/<scenario-id>

API key

Each request must include the x-api-key header with the application's API key.

This key is located in the Settings tab, Integrations section, API card. Click the key to copy it.

The API key gives access to your application. Do not share it and do not embed it in code running in a browser.

Variables

Variables define the data expected in the JSON body of the request. Each variable has a unique name and a type.

Type Expected JSON value Example
TextString"Smith"
NumberNumber42.5
Booleantrue or falsetrue
DateISO 8601 string"2026-11-02" or "2026-11-02T14:30:00Z"

All declared variables are required. The received values can then be used in the scenario steps.

Call example

The configuration window provides ready-to-copy code examples (curl, wget, fetch, PowerShell). Example with curl:

curl -X POST "https://<host>/api/workflow/<application-id>/<scenario-id>" \
  -H "Content-Type: application/json" \
  -H "x-api-key: <your-api-key>" \
  -d '{"customer":"Smith","amount":42.5}'

Responses

HTTP code Meaning
200 {"status":"queued"}The request is accepted, the scenario is queued for execution
200 {"status":"skipped"}The scenario has no steps, nothing is executed
400Missing or wrongly typed variable (details are listed in errors), or scenario that is not a Webhook scenario
401Missing or invalid x-api-key header
403Application not found
404Scenario not found

Execution is asynchronous: the response is returned immediately, without waiting for the scenario to finish. The execution result is available in the execution history.

Execution history

Scheduled, Webhook and Table scenarios have an execution history, available from the Execution history button in the list.

Executions can be filtered (All, Success, Failed). Selecting an execution displays its details:

  • the execution ID and status
  • the queue waiting time
  • the trigger variables (payload)
  • the console logs of the execution

The Delete all history button clears the scenario history. This action cannot be undone.
